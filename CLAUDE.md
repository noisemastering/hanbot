# Claude Code Project Notes

## Project Map (read this first)

**What it is:** a MX-Spanish sales bot for **Hanlob** (malla sombra / shade cloth) on **Facebook Messenger + WhatsApp**, plus a **React dashboard**. Ad clicks (click-to-Messenger / CTWA) enter the bot; it quotes products, shares Mercado Libre purchase links, and hands off to a human when needed. A correlation system attributes ML sales back to conversations.

**Two apps, one repo:**
- `bot-server/` — Node/Express backend (bot + API). Deploys to **Railway**.
- `dashboard/` — React app (analytics, conversations, Spec Ops). Deploys to **Vercel**.

**The bot brain (where most fixes go):**
- `bot-server/ai/index.js` — pipeline entry (persona, runs the engine).
- `bot-server/ai/workflow/index.js` — the **workflow engine**: per-turn logic = deterministic gates (borde, color, quantity, flow-switch, greeting…) that run BEFORE the LLM turn; a gate can short-circuit with a reply. Most bot behavior fixes land here.
- `bot-server/ai/workflow/setupContext.js` — builds the LLM system prompt (per-flow directives, promo preload, product knowledge).
- `bot-server/ai/workflow/tools.js` — the AI product-scope classifier (verdicts: `no_product|current|other_flow|needs_human|not_sold`) + measure/quantity parsing (`dimsOf`, `stripMeasures`, `qtyFromText`, `orderedQty`, `wantsWholesale`). **All measure/qty parsing MUST go through these — never a raw `\d+(x|por)\d+`.**
- **Active product flows are `Workflow` docs in Mongo** (reforzada confeccionada, sin refuerzo, rollo, borde separador, ground cover, complementos, cold-start) — inspect via the DB, not only files. Legacy flows (`ai/flows`, `ai/core`, the `*_FLOW.md` docs) coexist, but ad traffic runs on the workflow engine.

**Correlation (convo↔sale attribution):** `bot-server/utils/convoSaleMatcher.js` (tiered `classify()`), `runConvoCorrelation.js` (runner), `scripts/correlationHealthCheck.js` (17 invariants). Reads our OWN DB (ml_sales + conversations + clicks).

**Data:** production MongoDB Atlas (free-tier M0, ~512 MB cap). **The local server connects to the SAME prod DB** — be careful with writes/backfills.

## Bot Behavior Directive

**The bot must behave like a human, never like a bot.**

- NEVER force users to respond with numbers, codes, or specific formats
- ALWAYS understand natural language responses (e.g., "50 y 70%" instead of "2 y 3")
- NEVER say things like "Please select a number between 1 and 4" or "Reply with the option number"
- Parse user intent intelligently - if they express what they want, understand it
- Handle typos, informal language, and variations gracefully
- If the bot can't understand, ask naturally: "¿Cuál te interesa?" not "Invalid input, please try again"
- Conversations should flow naturally, not feel like filling out a form
- The bot represents a real business - it should feel like texting with a helpful salesperson, not a phone tree menu

**NEVER dump long product lists:**
- When listing products, ALWAYS check the count first
- If more than 3 options: show "desde X hasta Y" (smallest to largest)
- NEVER join all product names with " y " without checking count
- NEVER do `products.map(p => p.name).join()` on unbounded queries
- ProductFamily queries MUST filter by `parentId: null` for catalog overviews
- Any query that could return many items needs a limit or range display

- **The GROUND COVER campaign has its own opening and wording rules (2026-10-27, client spec).** The client wrote the campaign a two-part opener and four operating rules; an audit against the live flow found 4 of 6 unmet. Every gate that implements one is marked `§N` in `ai/workflow/index.js` and branches on `_gcFlow` (the flow whose families are ALL ground cover / antimaleza — the Raschel rollo flow carries a shade % in its names and is untouched). **§1 The opener is TWO messages.** A Ground Cover ad's first turn used to get `¡Hola! …¿En qué te puedo ayudar?` — no product, no prices, no invitation; the legacy per-product ad greeting in `index.js` has been dead since the engine took over greeting. Gate (a0-opener) now sends Mensaje 1 (the two full rolls with their prices + the benefit line) and Mensaje 2 (the invitation to quote, asking only the data we lack) as **separate bubbles** via `followUp`. Messenger has sent `reply.followUp` as a second message for a long time; the **WhatsApp processor had to learn it** (dual-channel rule) — a split reply was silently half-dropped there. The opener fires once (`state.gcOpenerSent`), only on the first bot turn, and only when the message carries nothing else to answer: **any digit** disqualifies it (a measure, an area like "3 hectáreas", a quantity) and so does a question about MEDIDAS, because answering only the price half of "Que medidas tiene y precio?" drops the other. Mensaje 2 **arms `pendingHandoff`** — it *is* the collect-before-handoff ask, the quoted rolls are full rolls an asesor always closes (ROLLO COMPLETO, 2026-10-23), and the existing guard drops the pending ask if the customer replies with a measure or another question instead of their data. The ad copy writes the prices as "$1,820 + IVA"; we show the IVA-included total ($2,111.20), which is the same money and the 2026-10-23 rule. **§2 Ask only what's missing — and the COLONIA was never captured at all.** It existed only in the dormant legacy `humanSalesHandler`, so "CP 76000, colonia Centro" had half the answer thrown away and the asesor — who quotes the freight from both — never saw it. Captured now next to the CP, persisted to `Conversation.neighborhood`, and printed in the location line of BOTH briefs (`handoffBrief`, `clientBrief`). The capture runs **ahead of the pending-handoff resume**, because that resume is the very turn the colonia arrives on and it returns before the passive capture block; it deliberately does not count as `gotContact` (a colonia reaches nobody). **§3 Never announce the canalización.** Every handoff said "¡Con gusto te paso con un asesor! 🙌" — narrating internal process, with the word this flow's own node prompt forbids ("usa especialista o supervisor"); the gate hardcoded it and overruled the prompt. On this campaign all three customer-facing literals now frame it as preparing the **cotización**. The escalation itself is unchanged. **§4 A bare LENGTH is a roll length.** The client's own example, "Gracias, quiero cotizar 10 metros", reached the bare-price gate (a0-bis) — "cotizar" matches it and there is no 2-D measure to stop it — and came back with the two 100 m rolls, so a customer who asked for 10 m never saw the 10 m price, which exists with a buy link. A length alone still can't be quoted, because the WIDTH is what moves the number, so the width is remembered on `state.gcWidth` and the length on `state.gcPendingLen` (either may arrive first) and the pair **synthesizes `dims`**, handing the turn to the deterministic quote path at (c) — which already owns the colour choice and the link. A length we don't cut offers the nearest one we do. This also fixes the **wrong-measure quote** reported the same day (wa:5219992598760, ad 120248845633580686): he asked for 2 m × 50 m and got "el rollo de **2x100 m** en **$1531.20**" — the price *and* the link of the 2x50 under the 2x100's name, then "$2111.20" for the same thing one turn later. The price and link were right because `resolvePrice` produced them; only the model's sentence was wrong, which is why the measure is now named by code. Battery cases `gc-apertura-dos-mensajes`, `gc-largo-menor-50`, `gc-largo-tras-ancho`, `gc-sin-anunciar-canalizacion`, `gc-datos-solo-los-que-faltan`, and a rewritten `gc-precio-sin-medida`. **The battery harness now judges `followUp` too** — reading only the first bubble made the opener look like it never asked for anything. Still the client's to reconcile: the price SHEET for the six CUT sizes is stale (2x50 reads $2,550 against $1,531.20 live, which would make a half roll dearer than the whole roll); live wins for cuts, so no customer sees it.
- **The GROUND COVER 24h follow-up (2026-10-27, client spec) — and it ships OFF.** The client's second Ground Cover document asks for ONE automated follow-up to conversations that went quiet, with rules about when it must NOT go out. It is `jobs/gcFollowUp.js`, its switch is `SystemState.gcFollowUp.engaged` (**default off**, flipped from the dashboard page or `POST /spec-ops/gc-follow-up`), and it is deliberately **not** gated behind `REMARKETING_ENABLED` — that env flag turned off the old 23h remarketing ping (`jobs/silenceFollowUp.js`) at the user's request on 2026-06-05, and this is a separate thing the client asked for by name. A DB switch, not an env var, because **the user never touches Railway config**. Two design decisions not to "simplify": (1) **nothing is scheduled ahead of time** — eligibility is derived from the transcript on every tick, so §3.1's "el tiempo de espera deberá reiniciarse si el cliente vuelve a escribir" falls out for free instead of being a stored timer with three places that must clear it (which is what the old silence follow-up has); (2) **the AI gate can only VETO.** §3.3 wants a judgement ("solo cuando exista una posibilidad razonable de que el cliente tenga una consulta o compra pendiente") and that is a model's job, but every hard exclusion in §4 is a regex in `HARD_EXCLUSIONS`, and the model is never asked to authorise a send — only to withhold one. A timeout, a bad key or a hallucination therefore costs a follow-up we might have sent; it can never put an unwanted message in front of a customer. Verified both directions: the gate vetoes 4 conversations that no regex catches (politely concluded, asesor already negotiating, wrong company, a lone 👍) and passes 3 genuinely pending ones. **Two bugs the first dry run caught, both of which would have hit real customers.** (a) The campaign filter ran in JS *after* the Mongo `.limit()`, so the first run considered **0 of 59** eligible conversations — the filter is in the query now. (b) With the 24h rule alone, 78 conversations were eligible **whose last message was in FEBRUARY**; a "¿encontraste lo que buscabas?" about an eight-month-old chat is a marketing blast, not "una continuación natural de la conversación", so `MAX_AGE_MS` caps it at 7 days. The spec doesn't state an upper bound; it plainly intends one. Also: **the active flow is authoritative** for deciding whose campaign a conversation belongs to — psid 39693838233563590 sits on the BORDE flow asking borde prices while still carrying `productInterest: "ground_cover"` from an earlier visit, and would have been followed up about a product he never asked about. §3.2's window is 7:00–20:00 México at a flat UTC-6 (no DST since 2022); every day counts as a "día permitido", since the spec excludes none and inventing weekend/holiday exclusions would silently drop follow-ups. One send per conversation (§7), claimed in Mongo *before* the send so a second tick can't double-send. A conversation where the customer wrote last is skipped: the bot owes them an answer, and a follow-up on top of an unanswered question is worse than silence. Every pass-over records a `skipReason`, so the campaign's silence is auditable — the dashboard shows the breakdown. **§5C is a gate, not a prompt** (a0-quejas, placed before BOTH the opener and the length gates, because a complaint is never a measure and a first-turn "nunca me dijeron el precio" is still a complaint — the opener used to claim it and reply with the price list, which is the brush-off being complained about): a complaint about the ATTENTION or the INFORMATION goes straight to a person, while a PRICE complaint gets the one authorized answer first (the smaller cuts genuinely cost less per piece) and only escalates if they insist — we never invent a discount. §5D sets `doNotFollowUp`. §6/§8 live on `Conversation.gcFollowUp` and `/gc-follow-up/stats`, rendered at **/playground/seguimiento-ground-cover** (sent, replied/not replied with %, recovered interest, the AI's reason buckets, the skip breakdown, and a **"Simular envío"** dry run that shows exactly who would be messaged without sending anything — use it before engaging the switch). Tests: `node scripts/gcFollowUpTest.js` (56 cases, no DB/LLM/network — the window boundaries, every §4 exclusion including the accented ones, and the flow-authority rule) plus battery cases `gc-queja-atencion`, `gc-queja-informacion`, `gc-queja-precio-opcion-autorizada`, `gc-queja-precio-insiste`, `gc-seguimiento-otra-medida`. **The accent trap, worth remembering:** a trailing `\b` after "compré" or "conseguí" can never match, because an accented vowel is not a regex word character — it silently disabled the "already bought" exclusion, the most load-bearing one in the list. Use `(?![a-záéíóúñ])` (the `END` constant) for Spanish word ends.
- **"El envío ya va incluido" is FALSE for a full roll (2026-10-27, client report).** On WhatsApp `wa:5217227079986`: "¿Cuál es el costo de envío?" → *"El envío ya va incluido en el precio, no se cobra aparte"*, and two minutes later his "2 x100" was quoted *"El rollo completo lo cotiza un asesor junto con el envío."* The bot contradicted itself about money inside two turns. The measure parse was fine (`dimsOf("2 x100")` → `[2,100]`, quoted correctly as a full roll); the bug was the two turns read together. Root cause: **`El costo del envío ya viene incluido en el precio` is a knowledge entry in ALL EIGHT workflows**, and it is true only of what is bought on Mercado Libre — a ROLLO COMPLETO carries no ML link by the 2026-10-23 rule and moves as freight an asesor prices by destination. Fixed in both places, because either alone would leave a hole: gate **(a0-envio)** answers a shipping question on the ground cover flow with BOTH cases every time (cuts 10/25/50 m include it; the 100 m roll is freight), ordering whichever applies first — an answer built from two true halves cannot be wrong — and it arms `state.zipAsked` because it asks for the CP (the UNPROMPTED capture path only accepts a bare number that exists in the ZipCode table, so "es el 50000" would be dropped and we'd ask twice). The knowledge text was corrected in the four flows that actually sell a full roll (Rollo, Ground Cover, Borde, Coldstart); the other four sell nothing but ML pieces, so theirs is accurate and was left alone. Same family as the borde's §3.5 mayoreo-shipping gate — a promise of free shipping on an order that does not ship that way. Battery case `gc-envio-rollo-vs-corte`. **Also: a COMPLAINT IS NOT A QUOTE.** The §5C handoff was running the cotización script at someone who had just said nobody answered them ("¿a nombre de quién, un teléfono, tu código postal y tu colonia?" — the brush-off all over again). `beginHandoff({complaint: true})` now asks for the one thing needed to call them back and nothing else. The battery judge caught this, which is the argument for keeping tone expectations in the battery and not only correctness ones.
- **Which AD a conversation came from, in the dashboard (2026-10-27, client report).** "When it's from WhatsApp we have no idea which ad it came from." The data was never missing — Messenger stores `referral.ad_id` and WhatsApp CTWA stores `referral.source_id` plus the ad's own `adHeadline`/`adBody`/`adSourceUrl`/`ctwaClid`, and **11/11 WhatsApp conversations in the last 30 days carry an adId** (Messenger 812/924). The dashboard simply never showed it: `/conversations/grouped` projected the raw numeric id and nothing rendered it, so the inbox was a list of phone numbers. `utils/adOrigin.js` resolves ids to names — `resolveAdNames()` batches Ad → AdSet → Campaign into **three queries for the whole page** (the existing `resolveByAdId` walks the chain one id at a time, which is right for one conversation and wrong for a list of thirty) with a 5-minute cache that also remembers MISSES, so an ad with no Ad doc doesn't re-query on every refresh. `originLabel()` falls back down a chain where every step exists for a reason: ad name → campaign name → **the WhatsApp CTWA headline** (the common case for an ad never imported into the dashboard — it is the only readable name we have) → `Anuncio <last 6 of id>` → null for genuinely organic traffic, which is a real answer and not a gap. Surfaced in two places: `GET /conversations/:psid/origin` (a separate endpoint because `GET /conversations/:psid` returns a bare ARRAY of messages that several callers depend on — widening it would be a breaking change for a display detail; it must be declared BEFORE `/:psid` or Express matches "origin" as a psid) feeds the chat modal header, and `/grouped` attaches `origin` to every row for the `AdOriginChip` under the phone number. Both show campaign/adset/ad/headline/id on hover, and flag an ad that is no longer ACTIVE.
- **A customer who says "lo voy a checar" is DEFERRING, not asking (2026-10-27, client report).** psid 29251119614512301 wrote "Voy a chequear", then "Ya le dije que lo van a checar", then "Una vez me den respuesta yo le digo" — and got the SAME sentence three times: *"¡Gracias! Ya te pasé los precios de los rollos de 6 m, 9 m, 18 m, 54 m. ¿Cuál te sirve y cuántos necesitas?"* Reported as "al final contestaba lo mismo". The borde nudge at §B is a **catch-all** for any turn carrying neither a length nor a count, and a deferral carries neither — so it fired every time, with no memory of having just fired. Pushing a buying question at someone who just said they have to check with somebody else is the "insistir" the client's own rules forbid. Fixed in two layers. (1) A flow-agnostic **deferral gate** right after the bare-greeting gate: it recognises the polite pause ("voy a checar/pensarlo/consultarlo", "yo te aviso", "una vez me den respuesta", "ya le dije que lo van a checar"), acknowledges it and stops selling. The replies **taper** — a warm line, then a short one, then "Quedo al pendiente. 🙌" — because repeating the same warm paragraph at someone winding the conversation down is its own kind of nagging. It is deliberately strict (no digits, no measure, ≤90 chars, and it never fires while a handoff is pending), so "voy a checar, pero ¿cuánto el de 18?" still gets its price. (2) A **repeat guard** in `ai/index.js` at the engine's single reply choke point: if a reply is byte-identical to the previous assistant turn it varies it rather than repeating. That is the last line of defence, not the fix — the engine has a dozen early returns that would each otherwise need their own guard — and it only ever APPENDS, because a repeated answer still beats silence. Deferral turns are exempt from it (`diagnostics.customerDeferred`), since that gate repeats on purpose and already tapers. Battery cases `borde-cliente-va-a-checar`, `borde-checa-pero-pregunta`.
